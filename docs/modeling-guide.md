# 建模指导：为一个真实目标定义可观测契约

建模的交付物包括模型声明、对象/事件语义说明、C adapter、属性 provider、生命周期协议和验证场景。只有 `.fg` 声明而没有后五项，读者无法知道数据是否真实、是否过期、是否能正确归属。

本章用 tt-emule 的 device/core/CB 说明方法；相同步骤也适用于软件队列、请求处理器或其他 cmodel。当前具体支持边界见 [能力范围](development-status.md)。

## 1. 从问题确定边界

先写用户要回答的问题，例如“设备 1 的 core(0,0)/CB0 每个 launch 有多少次 push 进入”。这个问题需要设备、核心、CB 和 launch 身份，push 事件及 phase；不需要先建模完整内存控制器和所有寄存器。

若问题改为“push 是否成功并提交多少页”，单纯 API entry/exit 已不足：exit 可能来自异常展开，n 可能只是请求量。此时先确认目标是否提供完成结果和实际提交量；没有就明确回答不了，或扩展模型，而不是把已有计数改个名称。

为第一版列出“可回答”和“尚不能回答”的问题，并让场景逐条验证。这比按宿主头文件机械生成全部接口更能保持语义准确。

## 2. 建一张实体设计表

| 实体 | 实际来源 | 局部身份 | 父对象 | 出生/死亡 |
| --- | --- | --- | --- | --- |
| launch 根 | 控制器执行边界 | adapter 定义的根身份 | 无 | begin/end |
| device | 当前执行设备 | 完整 u64 设备 ID | 根 | 本批次注册/结束 |
| core | 设备内坐标 | device + x/y | device | 本批次注册/结束 |
| CB | 本核心局部 CB | device + x/y + CB ID | core | 本批次注册/结束 |

还要规定 kind 编码及聚合对象含义，使局部身份在整个 launch 内唯一。声明一条树边之前，应能说明由谁证明父关系；不能从“地址相邻”或“恰好同线程”推断归属。

如果目标对象跨多个 launch 持续存在，而 registry 身份以 launch 隔离，需明确这是一份“本批次视图”，不是目标永久硬件 ID。跨批次报表可以按稳定业务属性汇总，但原始记录仍保留完整键。

## 3. 编写声明并解释字段

当前 tt-emule 声明可作为骨架：

```fg
pub object tt_emule { id: u64 }
pub object tt_emule.device { id: u64 }
pub object tt_emule.device.core { x: u32, y: u32 }
pub object tt_emule.device.core.cb { id: u32 }
```

每个字段另写一行语义说明：root.id 是 run 编号；device.id 来自执行 fiber 的 chip_id；x/y 是当前核心坐标；cb.id 是当前核心的 CB 编号。说明合法范围、是否允许零、是否能缺失、是否跨批次稳定。类型不能代替这些说明。

模型包使用 `Fingolfin.toml` 声明 package 名、version 和 source 目录，public 类型与 hook 按模块组织。固定布局 record 用于小型按值参数；不要将宿主内部类直接暴露成模型对象或任意内存布局。

## 4. 为每个 hook 写事件契约

| 必填项 | CB push 示例 |
| --- | --- |
| 语义 | 调用 cb_push_back 的进入或离开 |
| 归属 | 当前 device/core 下的 CB 实例 |
| 采集点 | 目标实际 API 实现的入口/离开 scope |
| 参数 | Observation、Core、cb_id:u32、n:u32 |
| 单位 | n 的目标 API 单位；不能擅自当字节数 |
| phase | 0=进入，1=离开；离开不承诺成功 |
| 缺失/异常 | 异常展开可能产生离开事件；进程崩溃不保证完整成对记录 |
| 重载/嵌套 | 转发实现可能形成嵌套 scope；列明采集哪些实现 |

声明签名只保证类型。若目标有更宽参数，要么模型保留宽度，要么在 adapter 显式拒绝不可表示值，不能静默截断。设备 ID 不能因为当前只测试 0/1 就降为 u32。

hook ID 是 adapter 与控制器的可信映射；记录名称、签名及编号对应关系，避免不同分组各自使用同号却被接到同一 Port。

## 5. 选择参数还是属性

某次调用的 n、phase、sequence 放在调用参数；对象归属设备、固定坐标可做身份属性。相同值需要同时存在于两处时，明确它们如何从同一目标上下文取得，并用测试比较一致性。

属性读取需要 provider；字段声明不会自动找到 C 对象。provider 接收完整路径，在选定实例上解析父链，并输出可复制的类型化事实。当前关系是单值 record，不能把“列出全部 CB”暗藏进一个字段读取。

对每条属性建立契约表：

| 路径 | 来源 | 阶段 | 失效条件 | 未知处理 |
| --- | --- | --- | --- | --- |
| device.id | 已注册父链 | Object | 对象/launch 结束 | unknown |
| core.x/y | 已注册身份 | Object | 同上 | unknown |
| cb.id | 叶对象身份 | Object | 同上 | unknown |
| 可变 occupancy（拟扩展） | 目标同步快照 | 尚无当前实现 | 每次占用变化 | 未实现前不得伪造值 |

## 6. 审慎声明 availability

只有能够证明对象寿命内不变，才声明 Object。精确路径声明例如：

```toml
[[availability]]
object = "tt_emule"
fields = ["device", "id"]
stage = "Object"
```

它不自动覆盖 device record、兄弟字段或另一种 anchor 写法。嵌套模式还可能读取中间 record；需为实际生成 reads 所需路径提供契约，不能只声明最后一个整数便假设整条路径都已提前可用。

没有声明则保留 Invocation，这是保守默认。Update 要求完整失效和重新发布协议；当前 Mount select 不刷新 facts，因此不要将一个动态字段标为 Update 后期待开关订阅自动更新它。tt-emule 当前策略要求准备时 facts 全知；不满足就拒绝策略绑定。

## 7. 把生命周期接到真实执行边界

实现 begin/end 时确认“宿主提交”和“实际执行”是否分离。deferred 模式应在实际执行时建立正确 scope，不能在提交线程上猜测执行设备。异常路径也需要 end；abort/进程崩溃无法用正常析构保证完成时，应声明边界。

对象结束前停止新路由、等待在途观察结束，排空状态后再失效键。provider 收集过程要锁住一致模型快照。宿主指针、encoder 代码和 runtime table 的寿命也需覆盖所有相关调用；registry resolve 成功不提供这些保活。

## 8. 从最小闭环逐步验证

1. 模型检查：声明、类型、hook、属性路径均通过编译。
2. 采集对照：一个真实调用的 device/core/参数逐项与目标上下文比较。
3. 路由对照：同 hook 不同对象各自计数，跨设备相同局部 ID 不混淆。
4. 生命周期：同程序重复 launch、槽复用、旧键拒绝、父树失效。
5. 属性：活跃时读对，失效后 unknown，64 位 ID 不截断，预算错误不发布部分 facts。
6. 结果：目标数据检查与观测输出检查同时通过。
7. 资源失败：容量耗尽、缺包、参数越界和 lease 未释放后能保留证据并恢复。

新增 hook 时先补能触发它的真实场景，再纳入覆盖矩阵。命中数量、参数完整度、数据正确性和错误恢复是四个维度，不能用一个百分比代替全部。

## 9. 模型随附说明模板

每个模型应有一份不依赖源码阅读的说明，至少包含：

- 要回答的问题与当前不支持的问题。
- 实体树、每类实例的身份组成和出生/死亡边界。
- 字段字典：类型、单位、来源、缺失值和稳定阶段。
- hook 字典：触发位置、phase、参数、重载和异常语义。
- provider 的快照与失效协议、原生值到 ABI 的转换规则。
- 资源上限、并发限制、输出归属和失败策略。
- 一个完整观测程序、配置、运行命令、预期输出与反例。
- 真实场景覆盖表、输入版本与报告阅读方式。
